# ADR-0050 The VOI extractor takes sides from patient coordinates and previews boxes before cropping
Status: Accepted · Date: 2026-11-09 (owner request for v3.2.0) · Extends: ADR-0014, ADR-0016

**Context.** The owner's batch VOI extractor (in the parent research repo) crops one VOI per kidney with a fixed configuration. It picks sides by the physical x of the two largest components and, for a lone kidney, compares it with the centre of the field of view, which is wrong when the patient is off centre. Some scans are prone or feet first. The workbench needs the same crops for other organs (lung, liver, pancreas, stomach, heart), per scan, per patient or in batches, and the user must see a candidate before writing files.

**Decision.**
1. One engine (`plugins/voi/engine.py`, numpy/nibabel/scipy, no `app` import) serves both the interactive routes and the `voi.extract` builtin task.
2. Volumes are read on their closest canonical RAS grid; **sides come from world coordinates** (the affine), never from voxel order, so prone, supine, head-first and feet-first scans give the same answer when the header is correct. Two components: the one further to patient right is `R`. One component: compared with the **body midline** estimated from the image (the median of the body's soft tissue, the table cut off), not with the grid centre. A component closer than 15 mm to the midline is flagged `side_ambiguous`; a blob that crosses the midline with both halves far from it is split (horseshoe kidney, joined lungs) and flagged `split_at_midline`.
3. Regions are presets (labels, laterality, minimum component volume, margin, minimum size in mm); only kidney and lung are lateral. Sizes are in mm, so the same setting works across voxel spacings.
4. The reviewer sees each candidate as the **middle axial slice of its crop** in a fixed display (anterior up, patient right on the image left, R/L marked) with the label bounding box and the crop box, plus its real size in mm. The preview is informative; it does not touch the main viewer.
5. Reviewer decisions (swap sides, exclude a VOI) are sent with the run's settings, so `run.json` records them with the reviewer (TSK-10); no separate event namespace.
6. Crops are NIfTI in RAS, written into the run's `output_dir` in the derived root with a `voi_catalog.jsonl` (R1). The image crop is registered as `image`, the mask crop as `sidecar`; neither becomes a project import or a segmentation set.

**Consequences.** The image's header decides where voxels are: a mask stored with another header (PanTS has LPS masks over RAS images, same shape) is read voxel for voxel on the image grid, which is how it was produced; reading each file with its own header mirrored those masks. A wrong image header (a prone scan stored as supine, a mirrored conversion) is caught only by anatomy: with liver or spleen labels the sides are corrected (`sides_from_anatomy`); without them the side stays Probable and the reviewer's Correct sides is the safeguard. An image-only check (bone or soft tissue asymmetry) was tried on 300 PanTS scans and rejected: the spine-position test flagged 3–7 % of normal scans (contrast aorta, sternum, the table) and the liver-asymmetry test agreed with the labelled anatomy in only 91 %. The midline estimate costs one downsampled read of the image per scan, cached with the candidates. The parent repo's `.npy` layout (`SAVE_AXES_ORDER: XYZ`) settles the legacy VOI axis order as `xyz` (SRC-12).

**Rejected alternatives.** Sides by voxel index (breaks on prone and flipped grids). Grid centre as midline (breaks off-centre patients). A separate review event namespace for decisions (a second record next to `run.json` for the same fact). Writing VOIs as a new import (the catalog can be imported later through IMP-10 when wanted).
