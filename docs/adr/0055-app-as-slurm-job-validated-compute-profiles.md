# ADR-0055 Running Radiology Workbench as a SLURM job with validated compute profiles
Status: Proposed (owner approved the decisions below 2026-11-11, conditionally: the transport of decision 5 is unresolved; accepted only after OPS-20 runs on a real cluster) · Date: 2026-11-11
Amends: ADR-0004 (session authentication, for the app job only; decision 4), ADR-0034 §6–7 (submission host, who chooses scheduler resources), ADR-0043 §5 and ADR-0051 §1 (HPC placement), and with them R2, OPS-18, OPS-22 and OPS-23 (decision 12). Extends: ADR-0054 mode 3. Does not change ADR-0053, the `local`/`server` backends or `rw-native.py deploy` on a server.

**Context.** OPS-23 puts the app and a light runner on "an approved service or submission node". A cluster may have none: login nodes that forbid computations, long-running services and processes that outlive the session rule out the systemd user service of OPS-22. The owner already runs the development servers inside a SLURM job with `dev_viewer.sh` (`start`, `stop`, `status`, `log` from a login node; VS Code "Forward a Port" to `node:port`); that shows the pattern works technically, not that a site approves it. The v1 SLURM adapter holds one fixed `partition`/`account`/`limits` set and asks for GPUs with `--gres` only. ADR-0004 accepts an unauthenticated app because it binds to localhost on a trusted host; a compute node is shared and reachable by other cluster users. Site facts and their evidence levels live in `../ops/HPC_ACCEPTANCE.md`, never in the code.

**Scope.** A private, single-user research application inside the user's own allocation. No public URL, DNS record, reverse proxy or internet-facing endpoint; no multi-tenancy, registration, accounts or external identity provider. The aim is private access with little to operate, not public web hosting.

**Decision (proposed).**
1. **The app is a CPU job.** On a cluster without a service node, the app and its light runner run inside one CPU-only SLURM job, never on a login node. `rw-native.py run [TAG]` starts a prepared native release in the foreground: app and runner as children, signals forwarded, exit when either child ends, no systemd and no unit files. `prepare` is unchanged but also runs inside an allocation, with conda from `CONDA_EXE` (a site module) and conda-forge only. `deploy` and `rollback` stay the server path, unchanged.
2. **Launching the app job** is one concern, separate from decision 9. `scripts/rw-app.sbatch` is the job script and, from a login node, the `start` / `stop` / `status` / `log` commands of `dev_viewer.sh`; those only call `sbatch`, `squeue` and `scancel`. Account, partition, wall time, CPUs, memory and paths come from the user's configuration, never from the script. One app job per user: a fixed job name, and `start` refuses while one is queued or running. `dev_viewer.sh` stays until the replacement passes the same lifecycle tests.
3. **Connection metadata.** Once the app answers its health check, the job writes `app-job.json` atomically (0600, in the 0700 state folder under HOME): job id, internal node name, port, bind mode, release tag, start and end time, and no secret. The port is the configured `PORT`, or the next free one on that node. `squeue` is the truth and the file a hint: `status` and `start` delete a file whose job is not running, and a clean stop deletes it.
4. **Session authentication, app job only.** It exists because a port on a compute node, loopback included, can be reached by other cluster users; it is kept as light as that needs. `run` in job mode creates a cryptographically random credential for each job, keeps it in memory and in its own 0600 file in HOME, and never writes it to the scheduler log, a URL, a command line or `app-job.json`. The user reads it on the login node and enters it once on a sign-in page; the app exchanges it for a session cookie bound to that job (`HttpOnly`, `SameSite=Strict`, and `Secure` whenever the app is served over HTTPS). Every API route, read or write, every event stream and any future WebSocket requires the session; only health and the sign-in page are open. State-changing requests also pass an `Origin`/`Host` check. Scripted clients (`ctflow`, `rw-mcp`, Electron) send the credential from the HOME file in a header. Comparison is constant-time and failed attempts are throttled. The credential dies with the job: the file is removed on exit, and one left by a killed job matches no process and is deleted by `status`/`start`. It is one credential for one Unix user's job, not an account or a role; reviewer names stay free text. Standalone and server deployments keep ADR-0004 unchanged: localhost binding, no credential.
5. **Access and transport.** Compute-node ports are never assumed reachable from outside the cluster, and an SSH-forwarded port encrypts only the part of the path that is inside SSH. The credential and authenticated requests must travel encrypted end to end. Default: the app binds the node's loopback and is reached through a forward that ends on that node inside an encrypted session (VS Code Remote on the job's node, R7; Electron mode 3 on the forwarded URL; Open OnDemand where a site offers it). If a site's forwarding can only reach the node's cluster interface, that port is exposed to the internal network: the operator must choose that bind mode explicitly, the exposure is documented for the site, and the segment needs TLS or a site-approved encrypted forward before it counts as a production transport. A plaintext login-to-compute segment, as in the tested `dev_viewer.sh` flow, is a development path, not a secure transport for credentials. Self-signed certificates are not an automatic default (open, below). Which segments are encrypted is a site fact: the transport stays unverified for a site until its acceptance confirms the real path.
6. **Lifecycle.** The job asks for SIGTERM before its time limit; the app stops taking work, the runner stops watching, and both exit. Submitted compute jobs are separate scheduler jobs: they keep running, and the next app job finds them again by name (existing recovery). After expiry the user runs `start` again and signs in with the new credential; all state is in HOME and the registered storage, none on the node. The app shows its own remaining wall time. Nothing resubmits the app job automatically.
7. **Compute profile.** A user-defined profile has an id, a human-readable name, SLURM account, partition, GPU count (at most 2 per job for now), GPU type when the scheduler reports one, CPUs, memory, requested wall time, the partition's discovered maximum, availability, and a validation status with its reason and time. Users create profiles in Settings → Compute from discovered, authorized accounts and partitions, with quantities inside the operator's limits; profiles live in the user's application state in HOME. The operator keeps control of which accounts, partitions and limits may be used: user configuration narrows that, never widens it. The GPU request form (`gres` or `gpus`) is a site setting, not a profile field. A deployment without profiles behaves as v1 (one implicit profile from the operator file).
8. **The runner owns the scheduler.** Discovery, validation, submission, cancellation, status and accounting queries all run in the runner; the API process executes no scheduler command (ADR-0034 §1) and reads the results through the existing runner records in the queue, with no new service. Discovery reads partitions, their state, limits and GPU types from `sinfo` and `scontrol show partitions`, and the user's accounts from `sshare -U`, with `sacctmgr` or other supported queries where needed. A profile is validated when created or changed and again immediately before each submission (`sbatch --test-only` on the exact request), because associations and limits change; it is `valid`, `rejected` with the scheduler's reason, or `unchecked` while the scheduler does not answer. For a task the browser sends a profile id only: never a flag, a free-text partition or a command string. No site's account, partition, limit or path is built into the code.
9. **Submitting compute jobs from the running app** is the second concern. Primary: the runner inside the app job calls `sbatch`, `squeue` and `scancel`, as v1 does from a submission host; scheduler commands run without the app job's `SLURM_*` and `SBATCH_*` variables, submissions keep `--export=NONE`, and a job script that starts steps unsets `SLURM_EXPORT_ENV` first. If a site does not support `sbatch` from a compute allocation, the only alternative is a submission service that the site itself supports (for example a scheduler REST API with the user's own token), behind the same submit/watch/cancel adapter. No login-node daemon, no relay over SSH, no manual outbox. Until such a mechanism is identified for a site, job submission there is **blocked**: the app still starts and its in-process tasks still run, and scheduler tasks are shown unavailable with that reason.
10. **UI extends existing surfaces; no HPC-only screens.** Settings → Compute: accounts, partitions, profiles, scheduler availability. Task form: profile choice, requested time against the partition maximum, and Check queue (the scheduler's start estimate) where Check GPUs is today. Jobs panel: scheduler state, pending reason, node, elapsed time and limit, and accounting such as `seff` where the site has it. Settings → Storage: ADR-0056.
11. **Storage on a cluster** follows ADR-0056: state, the registries and the credential in HOME; datasets and outputs in registered storage; temporary files, task HOME/TMPDIR, the Open-mode scratch and the DICOM inventory on job-local disk (OPS-24; the `slurm.scratch` default is unchanged). Releases and conda environments stay in HOME: they are read-mostly, made of many small files, and must not expire with a workspace. Durable results never live only on job-local disk. `run` probes `flock` and SQLite WAL on its state folder and refuses to start, with the reason, if either fails.
12. **Requirement amendments**, applied in DEPLOYMENT.md and AGENTS.md with the implementation. R2: no accounts and no user passwords; the app job's per-job session credential is the one exception. OPS-18: under `slurm`, the operator file sets the limits and may restrict accounts and partitions; the account and partition of a run come from a validated compute profile; the browser still sends ids only; at most 2 GPUs per run. OPS-22: `rw-native.py run` starts the same frozen release in the foreground without systemd; the service behavior is unchanged. OPS-23: where a site has no service node, the app and the light runner run inside a CPU scheduler job, started and stopped from a login node, with session authentication.

**Consequences.**
- + One production artifact (the native release) serves a server and a cluster, and the working `dev_viewer.sh` flow becomes the supported one.
- + A shared cluster no longer exposes projects to every user who reaches the port; other deployment modes are untouched.
- + Users pick a validated profile; a wrong account, partition or time is reported before a run is queued.
- − A sign-in step per app job, and scripted clients must read the credential file. − A site whose forwarding cannot end on the node has no accepted production transport until the open item is settled. − The app's lifetime is a wall-time limit, and the forwarded target changes with the node.
- − Remaining assumptions: the user's Unix account and HOME permissions are the root of trust; anyone who can read the HOME file, or act as that user, has full access; loopback on a shared node is still reachable by its other users, which is why the credential applies there too; the credential identifies a job, not a person, so the audit trail stays advisory (ADR-0004).
- − Every site-dependent item stays unverified in `../ops/HPC_ACCEPTANCE.md` until run on that site; local and fake-scheduler tests certify nothing (OPS-20).

**Open.** How to encrypt a cluster-interface segment where loopback forwarding is not available: a site-approved encrypted forward, a site-issued certificate, or a per-job certificate. A per-job self-signed certificate cannot be validated by a browser without a warning the user must click through, so it is not adopted before its validation and user experience are judged on a real site.

**Rejected.** A login-node service or `screen`; an unauthenticated app on a shared node; the credential in the URL or the job log; replacing ADR-0004 for standalone and server; accounts and roles; the app job holding GPUs for its tasks; `srun` steps for GPU work (ADR-0053); scheduler flags or free text from the browser (ADR-0034); site partitions, accounts or limits in the code; a one-shot login-node command or an SSH relay to submit compute jobs; trusting the connection file over `squeue`; automatic resubmission of the app job; Open OnDemand as the default.
