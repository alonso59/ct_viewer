# ADR-0056 Storage locations: one registry for local directories and managed HPC workspaces
Status: Proposed (owner approved the decisions below 2026-11-11) · Date: 2026-11-11
Extends: ADR-0005, ADR-0014, ADR-0030. Does not change R1, the operator's root policy (OPS-04, OPS-11, OPS-18), the project format, path aliases or ADR-0002 (no database).

**Context.** Allowed folders are operator settings: `ALLOWED_DATA_ROOTS`, `ALLOWED_DERIVED_ROOTS` and, separately, the runner's `source_roots`, `derived_roots` and `managed_datasets`. The two lists drift: a run on a dataset the runner does not list is accepted and then fails in the queue (ROADMAP, found 2026-11-10). A cluster adds storage that expires: managed workspaces (for example Lustre allocations made with `ws_allocate`) last a limited time and are deleted after expiry, while HOME is small and persistent. "Workspace" already means the app's project registry (`WORKSPACE_ROOT`), so the cluster kind is always a **managed HPC workspace** and the two are never merged.

**Decision (proposed).**
1. **Three places, configured separately.** *Application state* (central project registry, settings, storage registry, essential metadata; in HOME by the existing convention), *project storage* (storage locations, below) and *temporary storage* (scratch; job-local under SLURM). Standalone needs no SLURM, Lustre or `ws_*` tool: ordinary user-owned folders, with defaults under HOME.
2. **Storage location.** One model for both modes: a stable `id`, `kind` (`local_directory` or `managed_hpc_workspace`), canonical `path`, `access` (`read_only` or `read_write`) and a label. A managed workspace also keeps what the site last reported (filesystem, allocation name, expiry, extensions left, owner and group), each with the time it was observed. Availability, effective permissions and dependent projects are computed when asked, never stored as truth; a cached expiry or path is read again from the site before it gates anything.
3. **Registration stays inside the operator's roots.** The operator's allowed roots (environment variables and the runner's operator file) remain the policy. Settings → Storage registers a location only at or below one of them, and the registry can only narrow that policy: the browser never widens it. A discovered or group-shared workspace outside the allowed roots is shown with that reason and is not registrable until the operator adds its root.
4. **One registry, read by the app and the runner.** `storage.json` in the application state folder (0600, atomic writes, versioned) is the list of locations used for browsing, projects and task outputs. The runner accepts a registered location that lies inside its own operator roots, so a registered dataset needs no hand edit of the operator file and no runner restart. Roots configured today keep working as implicit locations: no deployment changes on upgrade.
5. **Access and role stay separate.** `access` says whether the app may write below a location at all. A project's `source` / `derived` roles (ADR-0014) and the managed folders of ADR-0030 still decide where: R1 holds inside a `read_write` location, and a `read_only` location is never written, not even by a probe.
6. **Backend validation, on registration and on use.** Canonical path; no traversal; containment checked after symlinks are resolved and again when a file is opened; exists and is a folder; effective read and write permission; a mount that is missing or does not answer is reported as unavailable, not as an error of the project. For `read_write`, "Test" creates and deletes one uniquely named probe file and touches nothing else. This limits what the app offers; it is not an operating-system sandbox. The app never uses root, and never changes ownership or modes.
7. **Setup is resumable.** Each location is saved on its own. An unavailable location never blocks startup, other locations or their projects.
8. **Compatibility.** No schema migration and no `format_version` change. Existing projects keep their paths, aliases and metadata and stay where they are; dataset-local state stays in the dataset (ADR-0030). New records add `storage_id` plus a relative path next to the absolute path, and resolution prefers the pair when the location is registered. Changing the default location for new projects moves nothing.
9. **The central registry outlives the storage.** The project registry in HOME keeps each project's id, name, storage id and last known path. When a workspace expires or disappears the entry stays and the project is shown with its storage unavailable; nothing is deleted, recreated or migrated.
10. **Explicit backup of project state to HOME.** A user action copies a project's state folder (curation, labels, settings; never images, masks, derived outputs or caches) into the application state. Limits, set by the operator: 1 GiB per backup and 2 GiB for all retained backups by default. The action first computes the estimated size, checks both limits and reports the effect on HOME; free space reported by the filesystem is shown but does not prove quota, so the limits are the gate. A backup is written beside the others under a temporary name and renamed only when complete; a partial copy, a filesystem error or a full disk removes that temporary copy and leaves existing backups untouched. Restore is equally explicit. Nothing is copied to HOME automatically.
11. **Managed workspace lifecycle is the user's.** The app discovers workspaces with `ws_list` where the tool exists, accepts a group's shared workspace by path within the user's effective permissions, and shows allocation, filesystem, folder, expiry, remaining time, extensions left, permissions and dependent projects. It warns before expiry and gives copyable `ws_extend` and `ws_allocate` commands with the right name, filesystem and an explicit duration. It never runs them.
12. **Gates.** A task whose output location is missing, read-only or expired is refused at submission, with the location and the fix named. Where expiry is known, a compute profile whose wall time exceeds the remaining lifetime is refused (ADR-0055 §8).
13. **Performance.** Scratch and persistent output stay distinct (ADR-0055 §11). Lustre striping appears only as documented site guidance; the app sets none and moves nothing.

**Consequences.**
- + The app and the runner cannot disagree about a registered dataset; the operator's policy is unchanged and still the outer bound.
- + The same Settings → Storage flow serves a workstation and a cluster; site tools are optional.
- + Losing a workspace loses its data, not the record that the project existed, nor its state where the user backed it up.
- − Backups are the user's to trigger and to keep current; an unbacked project on an expired workspace is gone. − Two path forms to resolve until old projects are reopened.
- Owners: PROJECT_FORMAT (PRJ), DEPLOYMENT (OPS), API. `ws_*` output formats, and allocation or renewal from inside a job, are unverified per site (`../ops/HPC_ACCEPTANCE.md`).

**Rejected.** The browser adding roots outside the operator's policy; a SQLite registry (ADR-0002; WAL on a network HOME is unverified); running `ws_allocate` / `ws_extend` / `ws_release` for the user before site acceptance; automatic copies of projects or data into HOME; moving project state out of the dataset; browsing the whole filesystem; moving data when the default changes; treating a stored expiry as authoritative; forcing existing projects onto storage ids; a second, HPC-only storage model.
