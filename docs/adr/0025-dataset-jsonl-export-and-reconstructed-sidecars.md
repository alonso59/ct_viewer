# ADR-0025 A JSONL whole-project export; reconstructed sidecars for `metadata-v1` imports
Status: Accepted · Date: 2026-09-25 · Amends: ADR-0020 §4 (Exports) · Refines: DCM-04/DCM-05

**Context.** Two related gaps surfaced auditing the import path for datasets that arrive as an already-converted `metadata.jsonl` (`metadata-v1`, SRC-03), not converted by this app's own `dicom.convert`:

1. The only whole-project merged view today is `exports/dataset_table.*` (CSV/Parquet, ADR-0020 §4). `VAR-08` explicitly excludes `raw_metadata` and full DICOM sidecars from ever becoming a variable — "all other raw tags are ignored" — so nothing not already flattened reaches that export, regardless of format; Parquet's support for nested/list columns doesn't help, because the exclusion happens upstream, at variable profiling, not at file serialization. This is exactly the class of metadata a JSONL-shaped source was originally chosen to carry: values that don't flatten cleanly into a table.
2. `metadata-v1` import only registers whatever fields the row already has. A row's `dicom_sidecar` field (INPUT_METADATA §`metadata.jsonl`) is a reference only — nothing generates or backfills it, so the Image view's "DICOM tags" section (DCM-05) has nothing to show for these items unless the source pipeline separately produced sidecars and the ref resolves. Most legacy datasets don't carry one (the reference example at this repo's root doesn't).

**Decision.**

1. **`exports/dataset.jsonl`** joins `dataset_table.*` as a second whole-project merged export (extends ADR-0020 §4; the CSV/Parquet export is unchanged, both are offered side by side). One JSON object per item, one line each: contract v1 core fields from the immutable snapshot, plus one key per active layer (phase, curation, labeling columns, …) — the same "layers, never a file edit" rule `dataset_table` already follows. Anything heavy or naturally per-file (a DICOM sidecar, an analyzer run's full annotation record) is a **reference** (a relative path into `sources/…`, `sidecars/…`, `tasks/runs/…`), never inlined: that is what makes JSONL worth having here over CSV — the file stays one line per item and streamable, while still naming where a non-scalar record lives instead of silently dropping it the way the table export must. `VAR-08` still governs what becomes a profiled *variable*; a ref only points at a fuller record, it doesn't re-include what `VAR-08` excludes. Sensitive fields (`patient_id`, dates) are excluded by default, same as `dataset_table` (`VAR-09`).
2. **Reconstructed sidecars on `metadata-v1` import**, opt-in. The import step (wizard, `metadata-v1` path) offers to synthesize a `sidecars/{filename}.dicom.json` per row from whatever converter-extra / DICOM-shaped fields the row already carries — an allowlist mapping flat field → DICOM tag (e.g. `kvp` → `(0018,0060)`, `window_center`/`window_width` → `(0028,1050)`/`(0028,1051)`, `manufacturer` → `(0008,0070)`, `study_uid`/`series_uid` → `(0020,000D)`/`(0020,000E)`, and the rest of DICOM_CONVERTER §Row fields' "converter extras"). It reuses DCM-04's file location and DICOM JSON Model shape so the Image view's "DICOM tags" section renders both kinds the same way, but a reconstructed sidecar always carries a top-level `_provenance: {source: "metadata-v1-import", fidelity: "partial", generated_at}` marker, and its `_omitted` note says it was built from an already-flattened row, not a full DICOM header — it must never be presented or treated as equivalent to a real DCM-04 sidecar. If the row's `dicom_sidecar` ref already resolves to a real file, nothing is generated; the real one always wins. PHI handling is inherited unchanged from DCM-05: derived-root-only, excluded from bundles/exports/logs, same `anonymize: basic` option.

**Consequences.**
- \+ `dataset.jsonl` gives the whole-project flat file the JSONL choice was originally for, without losing what `VAR-08` keeps out of the table export.
- \+ Reconstructed sidecars make "DICOM tags" usable for legacy imports instead of permanently empty, without ever duplicating or overwriting a real sidecar.
- − A reconstructed sidecar carries meaningfully less than a real one (only whatever the source pipeline happened to flatten); the `_provenance`/fidelity marker is load-bearing, not decorative — every reader must check it before treating the two as interchangeable.
- − Two ways to produce a per-item DICOM-shaped record (converted vs. reconstructed) is one more case to test and keep documented in step with each other (DICOM_CONVERTER.md, INPUT_METADATA.md).

**Rejected.**
- Generating reconstructed sidecars automatically on every `metadata-v1` import: forces a new derived artifact on imports that never asked for tag-level detail, and raises the odds of a synthesized file being mistaken for a real one — kept opt-in, offered as an explicit step/toggle in the wizard, never a silent default (mirrors the "reconcile, don't force" stance behind SRC-17's pattern suggester).
- Inlining full sidecar/annotation content into `dataset.jsonl`: defeats the point of a lightweight, streamable, one-line-per-item file, and duplicates data that already has its own file and its own PHI handling — a reference is enough.
- Reusing `dataset_table.*` (adding Parquet-only nested columns) instead of a new export: doesn't fix anything, since `VAR-08` drops the data before it ever reaches either table format.

**Doc updates required:** `docs/domain/INPUT_METADATA.md` (new IMP-15), `docs/domain/DICOM_CONVERTER.md` (DCM-04/DCM-05 note distinguishing real vs. reconstructed), `docs/domain/SOURCES.md` (SRC-03 note), `docs/domain/PROJECT_FORMAT.md` (`exports/` tree gains `dataset.jsonl`).
